ADR 能记录"为什么这么选"，记不了"这条路技术上通不通"。

> 依据（第 26 讲）：**做一个 spike 和做一个真产品，中间隔着 99%**——任何东西的总工作量里，99% 都是边角末节。

**这些不是"以后再做"，是"做了就说明 spike 失控了"：**

- ❌ 不碰 `index.html`（产品代码一行不改）
- ❌ 不碰备份格式
- ❌ 不做界面美化
- ❌ 不写测试（spike 的产出是"知道行不行"，不是可维护的代码）

> 依据（第 26 讲待办【整理者引申】）：只做那个最不确定的环节，做到「能看出行不行」就停手，**不要顺手做成半个产品**。

## 结果（2026-09-02）

### 已验证 · macOS 浏览器

| 环节 | 结果 |
|---|---|
| 服务端调 Azure TTS | ✅ HTTP 200，52992 字节，**3.0 秒** |
| 返回格式 | ✅ `MPEG ADTS, layer III, 128kbps, 16kHz` —— 与现有 1204 个文件同格式 |
| 存入 IndexedDB | ✅ 直接存 Blob，不转 base64 |
| **断网后播放** | ✅ **通了** —— 这是本次 spike 的判据 |
| 配额 | 已用 773KB / **可用 10241MB** |

### 由此得到的三个数字

- **每条约 52KB** → 10GB 可装约 20 万条，实际规模几十到几百条，**占用不到 0.5%**。存储容量不是约束
- **生成耗时 3 秒** → 收藏时会有可感知的等待，界面需要一个「生成中」状态，否则家长会以为卡住了
- **Blob 直存可行** → 不必转 base64（那会大 33% 且每次播放要重新解码）

### 已验证 · iPhone 主屏幕 PWA（2026-09-02 21:34）

| 环节 | 结果 |
|---|---|
| 服务端调 Azure TTS | ✅ 52992 字节，**1077ms** |
| 存入 IndexedDB | ✅ |
| **飞行模式下播放** | ✅ **通了** —— 21:34:49 播放时飞行模式已开启 |
| 配额 | 已用 0KB / **可用 39322MB（约 38GB）** |

**两个与预期相反的发现：**

- **iPhone 比 Mac 快 3 倍**（1077ms vs 3000ms）。原以为要给收藏加「生成中」状态防止家长以为卡住，1 秒的话可能不需要
- **iOS 配额比 Mac 大 4 倍**（38GB vs 10GB）。原以为 iOS 会小得多——按每条 52KB 算能装约 70 万条，**容量彻底不是约束**

**一个小异常**：`navigator.storage.estimate()` 报「已用 0KB」，但库里确实存着 52992 字节。iOS 的用量统计不准（延迟或粒度问题），**不影响功能，但配额数字不能太当真**。

### 仍然未知

- **系统在存储紧张时会不会清理 IndexedDB** —— 如果会，音频就不是"存下来了"而是"暂时在"。这个今天验不了，需要长期观察
- 隐私模式 / 清理站点数据下的行为
